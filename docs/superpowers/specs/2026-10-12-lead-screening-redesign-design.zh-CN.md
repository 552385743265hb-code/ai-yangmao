## 1. 为什么要做

ai-yangmao.com 的每条羊毛都由管理员人工审核。采集流程的目标是：只把新鲜、真实、在收录范围内的羊毛推给管理员，并且随着时间推移，推给管理员的东西越来越少。

现状并非如此。管理员反复看到：

- 已经批准过的羊毛，只是换了说法或换了来源被重新抓到（例如 8vk3 Qoder CN Qwen3.8-Flash 免费期延长、at2u WorkBuddy 大学生认证送 1,000 积分、智谱新用户注册送 2000 万 Tokens）；
- 已经拒绝过很多次的同类社区帖子（中转站、号池、非 AI 优惠、个人赠送）；
- 一批积压条目停在“系统审核”中，系统和管理员都无法处理；
- 有时效的羊毛（例如当天发放的重置卡）到得太晚，等管理员审到时已经快过期。

管理员对 Agent 今后职责的原话：

1. **自动采集线索并去重。** 只推送新鲜、真正的新线索；已经发布过的一律过滤。
2. **自我学习、提高精度。** 从过去的拒绝中学习，让后续线索更准确。社区来源的线索，必须由 Agent 先对照官方来源核实，再推送。
3. **自动审批。** 随着 Agent 学会各平台的公告位置、发布规律和更新周期，逐步减少人工审批，由 Agent 负责抓取和发布。

贯穿始终的三件事：**去重、线索精度、基于管理员历史决定和平台规律的自我学习。** 衡量成功的标准是管理员的人工审核量随时间下降。

管理员关于时效的进一步要求（2026-10-12）：羊毛不能在快过期时才推给管理员，导致审到时已经接近失效。紧急的一次性羊毛（例如当天发放的重置卡）一到就要直接排到审核队列最前面并发出通知，优先快速审批。**审核速度必须与羊毛的时效紧迫程度相匹配。**

## 3. 根本原因（来自代码）

以下是上述数据背后的机制，引用均指 `main` 分支。

1. **强制模式关掉了旧的查重。** 在 `IDENTITY_MODE=enforce` 且 `IDENTITY_CANARY_PLATFORMS=*` 下（2026-10-11 起上线），`/api/ingest/offers` 把每条羊毛交给 `adaptLegacyOffer` 后直接 `continue`（`src/worker/index.ts:296`）。`findDuplicate`、`crossPlatformDuplicate`、“与已拒绝记录重复则跳过”规则，以及抽取模型的 `sameAs` 合并都不再执行。
2. **身份判定几乎永远无法判“相同”。** `compareCandidate` 只在人工确认过，或双方都有经原文佐证且完全相同的 `occurrenceAnchor` 时才返回 SAME（`src/shared/identity/compare.ts:45`）。423 个历史实体回填时所有事实都是 unknown（`scripts/identity/backfill.ts:49`），抽取提示词又让模型在不确定时省略 `identityFacts`（`pipeline/llm.ts:354`）。产品和机制未知时，身份判定根本不检索历史（`src/worker/identity/service.ts:402`），直接返回 `needs_identity_review`。
3. **唯一的自动记忆只认完全相同的副本。** `findReviewedLegacy` 要求证据 URL、`valueText` 和原文摘录完全一致（`src/worker/identity/reviewed-legacy.ts`）。换个说法或换个来源就匹配不上。
4. **每抓一次就开一个任务。** 身份任务按候选 ID 建键（`identity:{candidateId}`，`service.ts:367`），同一条羊毛每被重新抓到一次，就多开一个任务。
5. **身份辅助 Agent 看不到内容，结论也被推翻。** 它看到的每个已有实体只有 `{id, platformId, revision, approvedVersionId, terms}`，没有标题、额度、摘录和 URL（`src/shared/identity/types.ts:46`）。除非确定性比较器已经同意，否则它的结论会被丢弃（`pipeline/identity-review.ts:40`）。它每轮最多处理 4 个任务，而且只能用每轮末尾的 90 秒（`pipeline/run.ts:454`）。
6. **拒绝无法举一反三。**
   - 线索关闭被记录为理由 `other`、范围 `observation_only`，绑定到一个 URL、一份精确正文哈希和一个候选 ID（`src/worker/identity/lead-closure.ts:19`）。
   - 羊毛拒绝默认范围为 `exact_version`（`service.ts:646`），换了说法的线索永远匹配不到。
   - 身份任务界面始终发送 `reasonCode:'other'`（`web/src/app.js:1889`）。
   - 抽取模型只能看到最近 10 条纠正。
7. **社区核验没有出口。** 身份准备要求每个来源都先被核实为官方页面，才会比对历史；社区来源永远不满足，所以 `pipeline/identity-workflow.ts:36` 跳过它们，任务每约 6 小时重试一次，无限循环。线索复核每轮只处理 4 条，共用一个经常处于冷却的搜索额度，还把额度花在明显不在收录范围内的帖子上。
8. **线索入库只按原始 URL 精确去重**（`leads_url_uq`），每次转帖都要花一次完整的模型抽取。
9. **自动上架无法挣到。** 需要每个信源连续 5 次原样通过；修改率约 75%，所以永远达不到。
10. **从头到尾没有任何环节按紧急程度排序。**
    - 管理员队列按发现时间排序（`src/worker/admin.ts:145`，这是管理员 2026-10-03 的决定，为了让新条目不打乱已经看过的条目）。
    - 审核提醒每小时发一次，每批最多 10 条（`docs/operations.md`）。
    - 线索每小时采集一次，但需要核验的线索随后会被数小时的退避卡住，与截止时间无关。
    - 身份准备有 72 小时 / 7 天的优先级（`src/worker/identity/preparation.ts`），但只排系统自己的工作顺序，不影响管理员看到的顺序。

    因此，一张当天发放的重置卡可能在系统状态中耽搁几小时甚至几天，然后再排在更早的常驻羊毛后面。

十条背后的共同模式：每次迭代都加了一道把不确定性转给管理员的防线，但从来没有给系统一种可信的方式，让它得出“这和 X 是同一条”或“这属于管理员会拒绝的那类”的结论。解决办法不是再加一层防线。

## 4. 目标、非目标、反目标

### 目标

- **G1 去重。** 关于已发布、已在待审或已被拒绝内容的线索或候选，不会再作为新条目出现在管理员面前。
- **G2 精度。** 管理员一贯拒绝的类别自动关闭。社区线索只有在官方来源确认后才会到达管理员。
- **G3 自我学习。** 管理员的每个决定（通过、带理由的拒绝、修改）都成为可复用的记忆。各平台知识（公告在哪里、周期性羊毛、更新节奏、易错点）由 Agent 维护，而不是手工维护。
- **G4 按表现解锁的自动化。** 当某个“平台 × 信源”与管理员判断的一致率经测量足够高时，解锁自动上架；管理员一旦纠正，自动撤回。
- **G5 没有死状态。** 每个条目始终有当前负责方（系统或人）和截止时间，不会无限期等待。
- **G6 速度随紧急程度提高。** 羊毛越紧急，在系统中流转越快，在管理员队列中排得越靠前。紧急的一次性羊毛会排在队列最前面，立即通知管理员，并带齐一步审批所需的全部信息（§6.12）。

指标（作者自定，待 §7 校准后复核）：

| 指标 | 目标 |
|---|---|
| 每周需要管理员处理的条目 | 自动关闭上线后 4 周内下降 ≥70% |
| 到达管理员的重复条目（管理员标记为“重复”） | ≤ 展示条目的 2% |
| 自动关闭被撤销的比例 | ≤3% |
| 从发现到送达管理员的时间，按紧急等级（§6.12） | P0 ≤30 分钟，P1 ≤2 小时，P2 ≤24 小时，P3 ≤72 小时 |
| 在系统负责状态中过期的羊毛 | 0 |
| 任一系统负责状态中最老的条目 | 不超过其等级目标 |

### 非目标

- 不改变“什么算羊毛”。收录范围继续以 `docs/data-contract.md`、`pipeline/learned-rules.md` 和 `AGENTS.md` 为准。
- 不重写公开网站、公开数据模型或估值流程。估值仍是管理员审核的数据。
- 不删除身份表。它们仍是实体、版本和决定的记录系统；本设计改变的是结论如何写进去。
- 不追溯撤下或重审已批准的羊毛。

### 反目标（即使一切“正常运行”也算失败）

- 错误的羊毛被自动发布，管理员是从用户那里才知道的。
- 真正的新羊毛，尤其是周期性羊毛的新一轮，被悄悄当作重复关闭，而且没有办法察觉。
- 管理员看不出系统为什么这么做，或者不能一键撤销。
- 改造又加了一道保守关卡，结果还是把所有东西都转给管理员。
- 模型开销在没有可见上限的情况下增长。

## 5. 管理员已做出的决定

- **允许自动关闭。** 当 Agent 有把握某条线索已经发布，或与管理员拒绝过的内容相符时，可以不经询问直接关闭；前提是管理员每天收到一份关闭清单，并且可以撤销其中任何一条。
- 社区线索由 Agent 先对照官方来源核实，再推送。
- 随着 Agent 学会各平台规律，逐步减少人工审批。
- **审核速度与时效挂钩。** 紧急的一次性羊毛立即排到队列最前面并通知，优先快速审批。羊毛不能在已经快过期时才送到管理员面前。
- **模型预算：** 每月约 $10，先试 OpenRouter 的免费模型。OpenRouter 账户中已有 $20 多的已购余额。
- §6 的方案原则上接受；本文获批前不做任何实施。

## 6. 设计

### 6.1 流程

```
采集（信源不变）
  │
  ▼
第 0 道闸  入口指纹（确定性规则，不调用模型；URL 键在 Worker，相似度在管线）
  │         已有决定的 URL / 几乎相同的转帖 → 挂接并关闭，留记录
  ▼
第 1 道闸  筛查 Agent（一次模型调用，带同平台全部历史 + 拒绝记忆）
  │
  ├─ 与已发布 / 待审重复 ─────────► 关联并关闭（自动）      ┐
  ├─ 与已拒绝重复 / 命中规则 ─────► 按类别关闭（自动）      ├─► 每日清单，一键撤销
  ├─ 不是羊毛 / 不在范围 ─────────► 按类别关闭（自动）      ┘
  ├─ 已发布羊毛的条款变化 ────────► 更新提案（管理员审，同现在）
  ├─ 不确定 ──────────────────────► 进入管理员队列，预选最可能的匹配
  └─ 新候选
        │
        ▼
     核验 Agent（找官方来源；先查平台画像里的渠道，再搜索；有时限）
        ├─ 确认 ──► 草稿 ──► 审批闸：该范围已解锁则自动上架，否则交管理员
        ├─ 被否定 ──► 关闭（自动，进每日清单）
        └─ 时限内未找到 ──► P0/P1：照样交管理员，标「未核实」
                            P2/P3：搁置（进每日清单），14 天后过期

学习回路（管理员每次决定或撤销之后）：
  决定记忆 · 拒绝规则 · 平台画像 · 一致性台账

紧急程度（贯穿每个环节，§6.12）：第 0 道闸定出 P0–P3 等级，筛查 Agent 修正；
  P0/P1 优先处理、核验时限短，并排在管理员队列最上方；P0 立即发 Telegram。
```

**社区线索**：筛查 Agent 在抽取**之前**，直接对线索文本（标题 + 抓到的页面）做判断，绝大多数噪声在花费任何抽取或搜索之前就被关闭。**官方页面候选**（信源监控）：照旧先抽取，再由筛查 Agent 把每个抽出的候选与该平台的历史比对。

### 6.2 第 0 道闸：入口指纹（确定性规则）

在任何模型调用之前运行，分两处：

- URL 检查在 Worker 的 `POST /api/ingest/leads` 中，按规范化键做索引查找；
- 相似度检查在管线中对照每轮的记忆快照（§6.10）进行。

具体规则：

- **先规范化 URL，再判断唯一性。** 复用 `normUrl`（去跟踪参数、去 `www`、twitter→x），并在明显的站点加规范键（linux.do 按主题 ID，忽略 slug 和楼层号；X 按 status ID）。规范化键与原始 URL 一起保存，唯一性按键判断。
- **URL 已有决定。** 规范化 URL 命中已关联或已拒绝的线索，或某条羊毛的证据 URL：把这次出现记到原决定下并关闭，不调用模型。
- **与已拒绝线索几乎相同的转帖。** 同一来源家族，标题 + 开头正文的二元组相似度 ≥0.9，且对方的拒绝是 90 天内的**权威决定**（§6.5.1）：按“与已拒绝线索 #N 相同”关闭。若转帖对应的线索已关联到某条羊毛，则关联到同一条羊毛（该羊毛本身的审核决定来自管理员）。
- **几乎相同的官方候选。** 同平台、标题相似度 ≥0.95、`valueText` 等价、领取窗口落在已有记录的窗口内，且该记录**不是**重置 / 轮次类羊毛：作为证据挂到已有实体上，不开任务。其他情况一律交给筛查 Agent。
- **预判紧急程度。** 第 0 道闸根据领取截止时间和确定性的措辞信号给出临时等级（§6.12），让 P0/P1 对象在同一轮中最先被筛查和核验。

第 0 道闸刻意保持狭窄，只低成本地去掉明显的副本，判断交给筛查 Agent。每次第 0 道闸关闭都是一条有记录的决定，会出现在每日清单中，和其他关闭一样可以撤销。

### 6.3 第 1 道闸：筛查 Agent（Screener）

**它看到什么**（由管线根据每轮记忆快照组装，§6.10）：

- 待判对象：标题、抓取到的正文（截断时带标记）、URL、来源、已有的抽取字段。
- **候选平台的全部记录**：已批准、待审、已拒绝和已结束的，每条带标题、valueText、类型、领取窗口、证据 URL、权益原文摘录、决定和理由类别。历史量很小（目前单平台最多 32 条）；每个平台按相似度和时间取最多 60 条，被截断时明确说明。
- 平台未知的线索：用 `platformMentioned` 找候选平台，再按相似度从全部羊毛和已决定线索中跨平台取前 20 条。
- **拒绝记忆**：最相似的 10–15 条被拒线索 / 羊毛及其类别，以及全部生效中的拒绝规则（§6.5）。
- 平台画像（§6.6）。
- 一份压缩的收录口径（来自数据合同和通用规则）。
- 旧启发式规则（`findDuplicate`、`sameEvidenceBenefit` 等）的相似度分数，只作提示，不作决定。

**它返回什么**（严格 schema，由服务端校验）：

```ts
{
  verdict: 'duplicate_published' | 'duplicate_pending' | 'duplicate_rejected' | 'rejected_by_rule'
         | 'not_a_perk' | 'update_to_published' | 'new_candidate' | 'unsure';
  matchId: string | null;        // 必须是提供给它的记录 ID 之一
  ruleId: string | null;         // 必须是生效中的规则 ID
  reasonCategory: ReasonCategory | null;
  occurrenceCheck: string | null; // matchId 指向周期性 / 重置类羊毛时必填：说明为何是同一轮
  confidence: number;            // 0..1
  evidenceQuote: string;         // 逐字摘自待判对象正文
  explanation: string;           // 一句简短中文，显示在每日清单中
  urgency: {                     // §6.12
    tier: 'P0' | 'P1' | 'P2' | 'P3';
    deadline: string | null;     // 带时区的 ISO 时间，仅当原文写明或可推导时填写
    signals: Array<'deadline' | 'same_day_one_time' | 'quantity_limited' | 'reset_event' | 'limited_time_unknown_date'>;
    quote: string | null;        // 逐字摘录；P0、P1 必填
  };
}
```

`ReasonCategory` 初始为：`relay_station`（中转站）、`account_pool`（号池）、`non_ai`（非 AI）、`personal_giveaway`（个人赠送）、`paid_bundle`（付费套餐自带）、`ordinary_discount`（普通折扣）、`model_news_only`（仅模型新闻）、`expired`（已过期）、`duplicate`（重复）、`wrong_platform`（平台归错）、`unverifiable`（无法核实）、`other`（其他）。类别可以增加；现有 `reason_code` 映射到这些类别。

**执行前的校验：**

- `matchId` 存在，且属于待判对象的平台（或属于提供给它的跨平台候选）；
- `evidenceQuote` 逐字出现在待判对象正文中；
- 组装上下文之后，待判对象没有变化；
- 周期性 / 重置类羊毛必须有 `occurrenceCheck`，且待判对象的日期不超出所匹配那一轮的范围。

任一校验失败，结论改为 `unsure`。P0/P1 的紧急判断如果没有逐字的 `urgency.quote`，降为确定性信号所支持的等级。`unsure` 的 P0/P1 对象仍按其紧急位置送到管理员。

**它被允许做什么：**

| 结论（置信度 ≥ 关闭阈值） | 动作 |
|---|---|
| `duplicate_published`、`duplicate_pending` | 关联线索 / 把候选作为证据挂到所匹配的实体；关闭针对它的身份任务 |
| `duplicate_rejected`、`rejected_by_rule`、`not_a_perk` | 按理由类别关闭，并引用对应的先例或规则 |
| `update_to_published` | 通过现有条款变更路径生成更新提案（管理员决定） |
| `new_candidate`（置信度 ≥ 单独的“新建”阈值） | 交给核验 Agent。核验 Agent 用官方来源确认后（官方页面候选则直接），通过服务端路径**新建实体和待审草稿**，操作人记为 `agent:screener`（效果等同于现在管理员在身份任务上回答“新活动”）。除非 §6.7 已为其范围解锁，草稿仍交管理员审批 |
| `unsure`，或任何低于阈值的结论 | 进入管理员队列，展示筛查 Agent 认为最可能的匹配，可一键选择“与 X 相同 / 新活动 / 拒绝：类别” |

它不能批准或发布（§6.7 除外），不能合并历史记录，不能删除任何东西，也不能修改已批准的记录。新建待审草稿不等于发布。

“关闭”和“新建”使用分别校准的阈值（§7）。错误的“新建”会把一份重复草稿放到管理员面前，管理员以 `duplicate` 拒绝；这次拒绝计入 ≤2% 的重复目标，并成为一条反例。

**模型与预算（管理员决定，2026-10-12）：每月约 $10，先试 OpenRouter 的免费模型。**

- **调用量。** 筛查 Agent 是一次聚焦、输出很小的调用，与抽取分开。每次调用约 5–10K 输入 tokens；每日调用次数见下表。
- **免费请求额度。** OpenRouter 免费模型限每分钟 20 次；账户累计购买额度不足 $10 时每天 50 次，满 $10 后每天 1,000 次（OpenRouter 限额页面，2026-10-12 核对）。管理员的账户已有 $20 多的已购余额，所以适用每天 1,000 次，无需再充值。这个额度按账户计算，所有免费模型调用共用：抽取的备用调用、估值和经验总结工作流都算在内。
- **每天 1,000 次够用吗？** 够用，约有 2.5–4 倍余量：

  | 工作 | 每天调用次数（估算） |
  |---|---|
  | 线索筛查（每天约 49 条线索，峰值 121） | 50–120 |
  | 官方候选筛查，按变化页面批量（上次全量轮次有 28 个页面变化 × 每天 4 轮；第 0 道闸先去掉一部分） | 约 110 |
  | 核验 Agent（每天约 10–20 个新候选，每个尝试数次） | 30–60 |
  | JSON 修复重试（约 10%） | 20–30 |
  | **稳定状态** | **约 210–260 次，繁忙日约 350–400 次** |
  | 一次性回填和校准（380 条重新筛查 + 182 条积压 + 最多 3 个模型 × 校准集） | 共约 2,000–2,500 次，分摊到约 5 天 |

- **每日分配，由预算台账执行。**
  - 每天预留 200 次给 P0/P1 紧急工作（§6.12）。
  - 非紧急筛查达到 800 次即停，确保预留部分不被占用。
  - 回填和校准每天最多 400 次，有紧急工作等待时暂停。
  - 通过限速（每分钟 ≤15 次）遵守每分钟 20 次的限制。
  - 免费模型的上游服务商在繁忙时也会返回 429：今天卡住的线索复核中有 4 条就是“模型耗尽”。遇到这种情况，P0 条目可以用付费兜底，其他条目等待。
- **固定模型，而不是路由。** `openrouter/free` 会把每个请求交给它选中的某个免费模型，OpenRouter 没有说明如何选择。在一个模型上校准的阈值不能套用到另一个模型上，所以：
  - 筛查 Agent 使用排好序的 1–3 个**固定 `:free` 模型**，在影子模式下用校准集（§7）实测后选定；
  - `openrouter/free` 和 Gemini 只作最后的兜底；
  - 每个结论都记录实际作答的模型；
  - **只有经过校准的模型给出的结论，才能自动关闭或新建草稿。** 其他模型的结论一律降级为 `suggest`（建议）。
- **输出不可靠。** 免费模型有时会返回格式错误的 JSON。允许带着校验错误重试修复一次；之后结论变为 `unsure`，或带截止时间等待。
- **模型下线。** 免费模型会被撤下（2026-10-07 曾有一个固定的免费模型返回 404）。若所有校准过的模型都不可用，筛查退回 `suggest` 模式，健康页和每日清单会说明。新增替代模型必须先在影子模式下重新校准。
- **付费兜底。** 每月约 $10 的预算是单独的台账行，用于：
  - 没有可用的免费校准模型时，处理 P0 条目（§6.12）；
  - 如果没有免费模型达到 §7 的精度要求，购买一个经校准的低价付费模型（OpenRouter 付费模型或 DeepSeek，两者都已可用）。

  现有抽取的 ¥10 上限不变。

**兜底规则。** 没有可用模型时，待判对象按其紧急等级设定截止时间等待；超期后进入管理员队列，标注“筛查不可用”，排在其紧急等级对应的位置。P0 条目先尝试付费兜底，等待时间绝不超过 P0 目标（§6.12）。除第 0 道闸的副本外，系统绝不在没有经过校验的模型结论时自动关闭。

### 6.4 核验 Agent（Verifier）：从社区到官方

复用现有线索复核和官方复核机制（`pipeline/lead-review.ts`、`pipeline/official-review.ts`、Exa 搜索），改动如下：

- **只对筛查 Agent 判为 `new_candidate` 的条目运行**（以及社区来源的 `update_to_published`）。噪声永远不会进入搜索，共用的搜索额度只花在真实候选上。
- **先查平台渠道。** 先读平台画像中已知的公告、价格、文档和 X 页面，找不到再用网页搜索。
- **时限随紧急等级而定（§6.12）。** P0：同一轮内立即核验，通过紧急通道重试；P1：每 2 小时一次；P2/P3：48 小时内最多 3 次。任何等级的核验时长都不超过距截止剩余时间的 25%。
  - **确认** → 生成带官方证据级别的草稿。
  - **被否定** → 以 `unverifiable` 类别关闭，进入每日清单。
  - **时限内未找到，P0/P1** → **照样交给管理员**，排在其紧急位置，标注「未核实」，并附上已找到的内容（候选官方页面和摘录）。P0 在发现 1 小时后送达，P1 在 12 小时后送达。把当天的羊毛搁置起来，它就失去了价值。管理员可以自行核实、标为实测，或者拒绝。
  - **时限内未找到，P2/P3** → **搁置**：不进主队列，在每日清单中列出并提供“我自己查”入口；14 天后（若截止更早则在截止时）以 `unverified_expired` 自动关闭。如果同一羊毛之后带着官方来源再次出现，第 0 道闸或筛查 Agent 会把它关联到被搁置的记录并重新打开。
- **平台不在白名单。** 如果核实到的发放方不是已准入平台，条目只交给管理员一次，询问“新平台：是否准入？”（平台准入仍由人工决定，见 AGENTS.md），不会无限重试。
- **专用时间片。** 每轮有专门的处理时间（不再用剩下的 90 秒），并有看门狗在 `/api/admin/health` 报告每个状态中最老的条目。

### 6.5 拒绝记忆与规则（从拒绝中学习）

#### 6.5.1 谁的决定算数

管理员授权的是自动关闭与**管理员拒绝过的内容**相符的条目。所以只有管理员的决定才是权威先例，模型做出的决定只作提示。

| 历史决定的来源 | 效力 |
|---|---|
| 管理员或具名审核员在后台界面 / API 的操作，包括管理员用仓库 `yangmao-review` 技能运行的 Agent 审核会话（写入前须管理员确认） | **权威** |
| 羊毛的通过与拒绝（目前所有羊毛决定都由人做出） | **权威** |
| 管理员在积压清理（§7）和每日清单中做出的确认（包括撤销） | **权威** |
| 管线研判拒绝（“模型判断不是 AI 羊毛”）、自动关联、身份模型建议、筛查 Agent 的结论 | **仅作提示**：作为上下文提供给筛查 Agent，但不能单独作为第 0 道闸关闭、自动关闭或规则提议的依据 |
| 无法归属的决定（380 条没有理由的被拒线索） | 重新筛查之前**仅作提示**（见下文） |

**归属。** 每条历史决定都标注 `actor_kind`（`owner` / `model` / `unknown`），依据 `review_decisions.actor`、`reviews.reviewer`、管线写入 `leads.raw` 的 `[研判]` 标记以及 `leads.resolution` 推断。新决定一律明确记录。

**重新筛查这 380 条。**
- 一次性回填会重新筛查这 380 条没有理由的被拒线索，而不只是给它们贴标签。
- 筛查 Agent 认同不在范围内的，保持拒绝并加上推断的类别，但仍只作提示。
- 它认为可能是真实羊毛的（如线索 5453 Zcode 3亿 tokens），在积压清理界面中列出一次，由管理员决定。
- 除非管理员操作，这些都不会改变线索现有的状态。

**筛查 Agent 仍然能自动关闭什么。**
- 先例记忆因此从约 55 条有理由的线索拒绝、184 条羊毛拒绝、管理员确认过的积压条目和回填抽查开始。
- 模型做出的拒绝不需要成为先例，自动关闭照样可行：不在范围内的类别通过**管理员批准的规则**来关闭。这些规则从历史中归纳，一次性批准。

#### 6.5.2 记忆分层

两层，都存在 D1 中，管线运行时读取：

1. **先例记忆。** 每条被拒线索和羊毛都带理由类别（管理员记录的，或 Agent 推断并标明为推断的）以及 `actor_kind`。筛查 Agent 按文本相似度检索最相似的先例；只有权威先例才能作为自动关闭的 `matchId`。在筛查中，这取代了实际上无法命中的 `observation_only` / `exact_version` 范围；现有 `review_decisions` 记录保持不变，供审计。
2. **规则。** 归纳出的、用自然语言描述的模式，例如“linux.do 上推广第三方中转 API 站（中转站 / 号池 / 公益站）的帖子不在收录范围内”。每条规则包括范围（全局 / 平台 / 信源 / 来源渠道）、类别、描述、示例引用、状态（`proposed` 提议 / `active` 生效 / `retired` 停用）、作者（管理员 / Agent）、命中次数和被推翻次数。
   - 当 Agent 在 60 天内看到同一类别、同一模式的权威拒绝 ≥3 次时，提出一条规则。
   - 提议的规则出现在每日清单中，可一键接受或拒绝。管理员自己写的规则立即生效。
   - 一条规则命中至少 10 次后，若被推翻比例超过 10%，自动停用。

**今后记录理由。** 每个拒绝操作（线索卡片、羊毛卡片、身份任务卡片）都要求点选一个理由类别，可附自由文字，取代写死的 `reasonCode:'other'`。这是一个很小的界面改动，没有它，学习会一直很慢。

**回填理由。**
- 一次性的 Agent 处理会重新筛查 380 条没有理由的被拒线索（§6.5.1），并给它们以及所有以 `other` 拒绝的羊毛加上推断的类别和一句理由。
- 管理员在同一个界面中随机抽查 30 条，同时查看“可能是真实羊毛”清单。
- 这次处理也会提出初始规则供管理员批准。从快照看，最明显的三条是：
  - 中转站、号池和公益站；
  - 非 AI 的消费优惠；
  - linux.do 上用户之间的赠送（与在那里发布的发放方官方赠送区分开）。

### 6.6 平台画像（学习平台规律）

D1 中每个平台一份画像（`platform_profiles`：JSON 文档 + 版本号），另有只追加的 `platform_profile_events` 日志，每条都注明是从哪个决定、羊毛或信源学到的。

画像包含：

- **官方渠道：** 公告 / 价格 / 文档 / 更新日志 URL、RSS、X 账号、公众号。每个渠道都统计已批准羊毛的证据实际来自它的次数。
- **羊毛规律：** 周期性羊毛（每月重置、注册赠送、每日签到）、地区区分（例如 Qoder 中国版与国际版是两条不同的羊毛）、命名习惯、已知易错点（“7天体验卡”是一张 7 天卡，不是 7 张卡）。
- **节奏：** 每个信源观测到的新羊毛间隔，以及最近一次变化。
- **准确度：** 该平台草稿各字段的修改率。

**谁维护：** 管理员对该平台每做一次决定或修改，画像 Agent（Profiler）就追加观察记录，每周合并整理一次。管理员可以在后台查看和编辑任何画像。

**初始化：** 迁移时导入 `pipeline/platform-notes.md` 的条目并保留日期。此后 D1 中的画像是现行来源，markdown 文件冻结为历史记录。这改变了 AGENTS.md 中“平台事实维护在 `platform-notes.md`”的规则，必须同时更新该规则。

**用于：**

- 筛查 Agent（上下文）；
- 核验 Agent（优先读取的官方渠道）；
- 抽取（平台易错点，以及该平台最近的字段纠正，取代全局最近 10 条）；
- 采集调度：按节奏建议抓取频率；当核实过的羊毛的官方 URL 不是已登记信源时，提议新增信源（新增仍需管理员一键确认）。

### 6.7 按表现解锁的自动上架（逐步减少审批）

用**一致性台账**取代 `cleanStreak ≥ 5` 规则。

- **预测。** 每份到达管理员的草稿，Agent 都记录它预测的决定（通过 / 拒绝 + 类别）和关键字段的预测值。管理员做出决定后，台账记录决定是否一致、哪些关键字段被修改。
  - **关键字段：** 类型、valueText 中的额度、资格 / 适用对象、领取窗口、creditValidity、models。
  - **非关键字段：** steps 措辞、tags、reviewMemo。
  - **不计入：** 估值。估值仍由管理员审核，本身不阻挡自动化。
- **范围：** 官方信源按“平台 × 信源”；核实过的社区线索按“平台 × 来源渠道”。已批准羊毛的更新单独成为范围，之后再解锁。
- **解锁：**
  - 当某范围最近 ≥15 个决定中 ≥93% 一致（决定和关键字段都一致），且没有“错误通过”（Agent 预测通过、管理员拒绝）时，系统提议为该范围开启自动上架。
  - 每次解锁都由管理员在每日清单中一键确认。
- **解锁期间：**
  - 该范围内通过现有硬性门槛的草稿自动上架，标记为“自动”，并在每日清单中列出，附“撤回”按钮。
  - 管理员对自动上架条目的任何纠正，都会让该范围降回人工审批并重新计数。
- **审批路径。** 目前没有任何 Agent 能批准：身份审批只接受 admin 或 reviewer 角色，旧的自动上架检查在强制模式下也不会执行。因此第 3 阶段新增一个范围很窄的 `agent:publisher` 操作人。
  - 它只能批准范围已解锁、且草稿通过发布检查的 `initial` 任务。
  - 它与管理员走同一个 `decideTask` 路径，以范围 ID 作为依据记录。
  - 它永远不能批准条款变更、证据重开或身份冲突。
  - 管理员原则上已同意（目标 3）；每个范围仍须单独确认。
- **自动上架羊毛的估值。** 羊毛上线时使用入库步骤已经计算出的估值，在后台卡片和每日清单中标为**系统估算**（未经管理员审核）。管理员按自己的节奏审核估值。未审核的估算不会阻挡发布，也不会被显示为管理员已确认。
- **对外推送。** 自动上架的羊毛**在 24 小时内不进入推送渠道**（飞书群日报、每小时加急推送、RSS），让管理员的每日清单先看到。在这个窗口内撤回，就等于从未对外发布。例外：24 小时内截止的羊毛，只有当其范围最近 15 次自动上架零纠正时才进入加急推送；否则等待管理员。
- **永远不自动**（现有硬性限制不变）：
  - 未准入平台；
  - 员工账号来源；
  - 只有社区证据；
  - 有会员资格要求；
  - 缺少权益 / 资格 / 有效期的官方原文摘录；
  - `tested` 级别。

由于目前 75% 的审核是修改，按表现解锁的自动化取决于抽取质量的提高。把各平台的纠正反馈给抽取（§6.6）是主要手段；每个画像中的字段修改率可以看出是否见效。

### 6.8 管理员看到的界面

- **每日清单**：出现在后台（新增“系统已处理”区）和现有 Hermes Telegram 09:00 日报的一个小节中。内容包括：
  - 按结果分类的数量；
  - 每条自动关闭的条目，附匹配对象 / 规则、一句理由和**撤销**按钮；
  - 被搁置、未核实的条目；
  - 提议的规则；
  - 提议解锁自动上架的范围；
  - 自动上架的条目，附“撤回”按钮。
  - 自动关闭上线的头两周，清单列出每一条关闭；之后仍列出全部关闭，但随机标出 10% 供抽查。
- **撤销**：一键完成。它把对象重新放回管理员队列，附上筛查 Agent 的理由，并记录一次推翻；这次推翻会成为先例、规则和自动化范围的反例。原结论和推翻记录都保留。
- **管理员队列的排序：**
  - 先 P0，再 P1、P2、P3（§6.12）。同一等级内，距截止剩余时间最少的排在最前。
  - P0 和 P1 位于审核页顶部固定的「紧急」区，带实时倒计时。
  - P3 保持发现顺序，非紧急条目仍不会被打乱。
- **管理员队列卡片**：每个条目都显示紧急等级和倒计时，以及筛查 Agent 认为最可能的匹配和置信度，可一键选择“与 X 相同”“新活动”或“拒绝：类别”。
- **P0 立即通知**：几分钟内发出 Telegram 消息，不分时段，带齐决策所需的全部信息；管理员回复「通过 <短码>」即可批准（§6.12）。
- **健康状态**：各状态中最老条目的等待时间、筛查 / 核验吞吐量、撤销率和模型花费，显示在 `/api/admin/health` 和后台健康页。

### 6.9 对现有身份机制的改动

- 筛查 Agent 的重复结论通过一条**新的服务端路径**写入身份表：
  - 把候选以 `evidence_only` 挂到所匹配的实体；
  - 写一条 `review_decisions` 记录，动作为 `same`、操作人为 `agent:screener`、依据为筛查决定 ID；
  - 取消已开的身份任务。
  - 版本、发布修订号和通知都不变。
- 筛查 Agent 的拒绝通过 `closeIdentityLead` 写入，附理由类别和所引用的先例或规则。
- 身份任务按羊毛建键，而不是按候选：同一条羊毛已有未结任务时，新候选并入该任务。
- 现有身份模型辅助（`pipeline/identity-review.ts`）和每轮末尾的 90 秒时间片停用，由筛查 Agent 自己的时间片取代。
- 线索研判的抽取提示词不再附带全部羊毛的索引，去重交给筛查 Agent，抽取提示词因此变小。
- `IDENTITY_MODE=enforce` 保持开启。第 0 道闸和筛查 Agent 在它之前运行，根本原因第 1 条中的绕过因此不再造成影响。旧启发式规则只作为筛查 Agent 的提示继续使用。

### 6.10 在哪里运行

- **筛查、核验和画像 Agent** 在管线中运行（GitHub Actions，Node），那里已经有模型和搜索的访问权限以及预算台账。
- **D1 使用 Workers Paid**（管理员，2026-10-12）。没有每日读取上限，每月包含 250 亿行读取，所以设计优先追求简单，而不是压缩读取量。
  - **记忆快照。** 每轮开始时，管线拉取一份精简的**记忆快照**：羊毛、已决定的线索、标签、规则和画像。总共几千行，每轮都重新拉取，不需要维护跨轮缓存。相似度和上下文组装在 Node 中对照快照完成。按每天约 28 轮计算，约每天 10 万行，相对每月额度可以忽略。
  - **Worker 用索引查找来校验并执行结论。** 确认待判对象和所匹配的记录没有变化、ID 存在，然后提交。
  - **线索研判的抽取提示词不再附带完整的羊毛索引。**
  - **读取有统计。** 与筛查相关的读取按轮统计，显示在 `/api/admin/health`。
  - **健康监测阈值。** 现有健康监测中的 D1 用量提醒仍按免费版数字计算（每天读取 500 万行 / 写入 10 万行），应改为付费版的每月额度，以免误报。这是一项相关的小修复，列在这里以免遗漏。
- **Worker** 负责校验结论并原子地执行，执行沿用现有的 `commitIdentityMutation` 批处理模式。
- 筛查和核验在**每小时的快速轮次**中运行，有自己的时间预算，排在官方信源全量轮次之前。每轮中先处理 P0，再处理 P1，然后才是其他工作。
- **紧急通道。** Worker 每 15 分钟运行一次定时任务，执行一条索引查询：是否有 P0/P1 条目在等待系统工作（筛查、核验重试或生成草稿）？如果有，就派发一个只处理这些条目的精简管线任务（管线已经支持定向运行，例如 `LEAD_REVIEW_IDS`）。没有紧急工作时它什么也不做，不派发任务，也不消耗 GitHub Actions 分钟数。常规采集仍为每小时一次。
- **立即提醒管理员**：由 Hermes 新增一个每 5 分钟的检查。它读取一个很小的索引接口（管理员队列中尚未通知的 P0 条目），并通过现有的占位 / 回执台账发送。待定或结果不明的投递绝不自动重发。
- 运行模式由 `SCREENING_MODE = off | shadow | suggest | auto` 控制：
  - `shadow`（影子）只记录结论；
  - `suggest`（建议）把结论作为预选项展示给管理员；
  - `auto`（自动）直接执行。
  - 单条规则和单个自动化范围也可以单独关闭。

### 6.12 紧急程度与审核速度

管理员的要求（§1、§5）：审核速度与时效紧迫程度挂钩，羊毛不能在已经快过期时才送到管理员面前。

**等级。** 每个对象在第 0 道闸根据领取截止时间和确定性的措辞信号获得等级，由筛查 Agent 修正；截止信息变化时以及随着时间推移，等级会重新计算。

| 等级 | 条件 | 系统目标（发现 → 送达管理员） | 通知管理员 | 队列位置 |
|---|---|---|---|---|
| **P0 立即** | 24 小时内截止；或当天一次性发放（重置卡、兑换码、“仅限今天”）；或限量且正在被领取 | ≤30 分钟 | 立即发 Telegram，不分时段；若 30 分钟内未处理，再提醒一次 | 「紧急」区最上方 |
| **P1 加急** | 24–72 小时内截止；或限量但没有当天信号 | ≤2 小时 | 下一次每小时提醒，排在该批最前 | 「紧急」区，P0 之下 |
| **P2 限时** | 3–14 天内截止；或标“限时”但未写截止时间 | ≤24 小时 | 每日清单 | 常驻条目之上 |
| **P3 常驻** | 无截止、常驻额度、申请制，或截止在 14 天之后 | ≤72 小时 | 每日清单 | 最下方，按发现顺序 |

同一等级内，按**最晚有效审核时间**排序，即截止时间减去最短公开窗口（P0 为 2 小时，其他为 12 小时），再按发现时间排序。

**信号。**
- 明确的 `claimEnd` 和时区，包括通过现有 `campaign-deadline` 处理的相对时长。
- 一次性或当天发放：重置活动、兑换码、“今天 / today only”。
- 数量限制：“限量 / 先到先得 / 发完即止 / 手慢无 / first N”。
- 平台画像中的历史，例如该平台的体验卡以前在几小时内就领完了（§6.6）。

防止虚假紧急：
- 只标“限时”而没有日期的，最高只到 P2。
- 既没有日期也没有数量限制的煽动性措辞，永远不会产生 P0。
- 任何 P0/P1 判断都需要逐字摘录。除非筛查 Agent 为不同等级给出依据，否则沿用第 0 道闸的等级。

**系统内的快速通道。**
- **处理顺序。** 每轮中，P0、P1 在第 0 道闸、筛查、抽取和核验各环节都最先处理，并使用每日 OpenRouter 额度中的预留部分（§6.3）。
- **核验时限短（§6.4）。**
  - P0 在同一轮内核验，通过紧急通道重试；即使 1 小时后仍未核实，也会送到管理员，标注「未核实」。
  - P1 若 12 小时后仍未核实，同样标注后送到管理员。
  - 核验时长绝不超过剩余时间的 25%。
- **紧急通道**每 15 分钟一次，只在有紧急系统工作等待时运行（§6.10）。
- **没有模型也不能成为延误的理由。** 如果没有可用的免费校准模型处理 P0 条目，就用付费兜底；如果付费兜底也失败，条目不经筛查直接送到管理员，并加以标注。
- **去重照常适用。** 筛查 Agent 认出与已发布羊毛重复的 P0 条目照常关闭：紧急并不意味着是新的。

**让管理员快速审批。**
- **P0 的 Telegram 消息本身就足以做决定。** 消息包含：
  - 短码、标题和额度；
  - 截止时间和倒计时（平台时区与北京时间）；
  - 领取资格；
  - 官方或现有最佳证据的链接和摘录；
  - 已完成的发布前检查；
  - 筛查 Agent 的查重结果。

  管理员回复「通过 <短码>」（即 Hermes 现有的 `ym approve`），或从链接打开后台卡片。
- **P0/P1 后台卡片一键可批。** 卡片显示倒计时，“通过”按钮放在最前；缺失的必填字段由 Agent 预先填好并标出，草稿无误时一键即可批准。
- **按表现解锁的自动化。** 在已解锁自动化的范围内（§6.7），P0 条目无需等待管理员就会自动上架；如果其范围最近 15 次自动上架零纠正，则不受 24 小时推送暂缓的限制。

**来得太晚、已无价值时。**
- 如果条目送到管理员时已过了最晚有效审核时间，它仍显示在最上方，标注「即将截止」，并可一键「作为历史上架」。
- 如果在等待期间过了截止时间，它会自动变为「作为历史上架」建议，并移出「紧急」区。任何条目过了截止时间都不会再停留在紧急状态。

**按等级统计：**
- 从发现到送达管理员的中位数和最长时间；
- 从通知到管理员做出决定的时间；
- 在系统负责状态中过期的羊毛数（目标为 0）；
- 在等待管理员期间过期的羊毛数；
- 管理员事后认为不紧急的 P0 通知占比，用于调整信号。

### 6.13 社区来源（linux.do）

管理员提议（2026-10-12）完全停用 linux.do，因为它的大部分线索都是噪声，而且多数真实羊毛在官网上也能找到。数据（§2）证实了噪声问题，但也显示 linux.do 是若干已批准羊毛的唯一来源，主要是难以发现、时效性强的那类：应用内赠送、分享链接式体验卡、新平台。

**已决定（管理员，2026-10-12）：保留 linux.do，只作发现来源，不占用管理员任何精力：**

- **入口标题规则（第 0 道闸，经管理员批准）。** 标题带有以下内容的 linux.do 线索，在入口直接关闭，不调用模型，也不进入任何队列：
  - 【富可敌国】标签；
  - 中转站 / 号池 / 公益站措辞；
  - 日常非 AI 优惠。

  按历史数据，这能去掉约三分之一的噪声，且不会丢掉任何真实羊毛。
- **未经核实不送给管理员。** linux.do 的条目只有在核验 Agent 找到官方来源后才会送到管理员，或者按 §6.12 作为未核实的 P0 送达。
- **每次发现都让监控变得更全。** 当一条 linux.do 线索引出一条经核实的羊毛时，平台画像会记下这条羊毛的官方渠道，系统提议把它加入受监控信源（§6.6）。下次官方监控就能直接抓到。
- **独有产出检验。** 每个社区来源都统计它首先发现、且没有任何受监控官方信源覆盖的已批准羊毛数量。如果 linux.do 连续 4 周的独有产出为零，系统会提议停用它，管理员一键确认即可。

**曾考虑但未采用：现在就停用 linux.do。**这会立即去掉 linux.do 的全部噪声，包括 103 条卡住的线索复核中的 101 条。按最近 13 天估算，代价是每两周大约漏掉 2–4 条已批准羊毛，大多是时效很短、没有其他渠道能及时提醒管理员的那类。无论选哪个，卡住的 linux.do 条目都会在积压清理（§7）中关闭。

## 7. 积压清理（一次性，同时用于校准）

1. 以 `suggest` 模式对 77 个身份任务和 105 条复核中的线索运行筛查 Agent。
2. 管理员在一个批量界面中审阅这些建议（接受，或带类别推翻）。从快照看，约 65–70 个身份任务应作为已有记录的重复关闭，103 条线索中的大多数应按类别关闭。
3. 这些经管理员确认的结果，加上 30 条理由抽查（§6.5），构成**校准集**。
   - 每个候选模型（§6.3）都在影子模式下用这个集合实测。
   - 每个模型分别设定两个阈值：“关闭”（精度 ≥97%，且周期性羊毛零误关）和“新建”（错误“新建”≤2%）。
   - 达不到两个阈值的模型，永远不用于自动操作。
